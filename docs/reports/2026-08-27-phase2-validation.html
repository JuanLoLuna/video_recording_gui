Video Recorder Phase 2

Rotating a continuous recording into fixed-size video segments without losing a frame at any boundary — proven under real repetition and a real camera fault, with the cross-repo work still needed before it's safe to deploy in the study.

00

Summary

Phase 1 made a 10-day session survivable; Phase 2 makes it safe to actually hold on disk. A single continuous AVI hits its 4 GiB RIFF ceiling in well under 40 minutes at the measured bitrate, and a corrupted file would lose the whole session instead of one chunk. This phase rotates recording into ~15-minute segments the app owns end to end — pre-arming the next writer, swapping at the boundary, closing and renaming off the acquisition thread — and ties Phase 1’s camera-fault watchdog into rotation, so a recovered fault always forces a fresh segment.

Eight commits shipped on video-segmentation, backed by 160 unit tests (62 new since Phase 1) and two real test sessions on the acquisition rig: a 32-segment, ~10-minute continuous rotation stress test, and the same camera unplug/replug used in the Phase 1 report, now examined for its rotation behavior specifically.

03

What broke, and how it’s handled

Three findings this period. The first broke the app outright on first launch; the other two were caught only by reading the actual test data rather than by inspection.

01CameraController crashed on construction: AttributeError on target_frame_rate
Symptom
Every CameraController() construction raised AttributeError: 'CameraController' object has no attribute 'target_frame_rate' — the app couldn't start at all.
Cause
→ The new rotation state block in __init__ computed segment_frames_for(self.target_frame_rate) earlier in the constructor than the pre-existing self.target_frame_rate = 30.0 assignment — a plain ordering mistake introduced while inserting the new block.
Found by
The user's first real launch attempt on the acquisition machine — a class of bug that py_compile/syntax checks can't catch, and that couldn't be caught in this session at all without the real hardware, since CameraController can't be constructed without PySpin.
Result
Fixed — the computation moved to immediately after target_frame_rate's own assignment.
02Segment manifest mixed two different clocks in the same row
Symptom
opened_at (e.g. 85017.9) and closed_at (e.g. 1787870714.4) in _segments.csv were never comparable — a consumer computing segment duration from them would get a meaningless multi-billion-second difference.
Cause
→ opened_at used time.monotonic() (an arbitrary reference point) while closed_at used time.time() (Unix epoch). close_duration_s itself was correct, computed separately as a proper monotonic delta — only the two absolute timestamps disagreed.
Found by
Reading the actual _segments.csv from the fault-recovery test rather than inspecting the code in isolation.
Result
Fixed — opened_at switched to wall-clock, matching closed_at and first/last_system_time in the same row.
03The metadata "segment" column bumped one frame before "segment_file" did, on a fault
Symptom
At the fault boundary, frame 173 showed segment=1 but segment_file still pointing at the old segment — breaking the documented invariant that both columns change together on a fault-forced rotation.
Cause
→ The video/frame alignment itself was exactly correct — frame 173 genuinely was the old file's 173rd and final frame. The bug was that self._segment_tracker.current_segment (feeding the segment column) bumps immediately when a reinit succeeds, for prompt events-log writing, while segment_file only bumps at the next rotation check — one frame later in this case.
Found by
Reading the exact fault-boundary rows of the real _metadata.csv line by line, cross-checked against _segments.csv's frame_count.
Result
Fixed — a new field, copied from the tracker only at the moment of the actual file swap, so both columns now change on the same row.

None of the three affected the video or frame data itself — all were bookkeeping-column issues in sidecar files, found only because real test data was actually read row by row rather than summarized. That is the generalizable lesson: a clean pass/fail check (row counts match, gaps are zero) proves the mechanism works, but only reading the actual rows catches a mismatched clock or an off-by-one-frame column.

04

Open items

inventory.py collision — open, other repo, non-patient path only

smart_sleeve_data_processing/pipelines/reconcile/inventory.py's norm_video_key strips the -NNNN suffix and uses the result as a dict key on both sides of sync reconciliation. Every segment of a session collapses to one key, last-writer-wins — 32 of 33 segments would be silently dropped, never copied, never reported missing. Still not fixed, but scoped: this only affects the existing Box-based reconciliation pipeline for non-patient data. Patient recordings use a separate pipeline that never lands in Box, so this no longer gates using segmented video for the study.

Merge to main — done

video-segmentation merged to main on 2026-08-27, since the inventory.py blocker turned out not to apply to the patient recording pipeline.

video_fiducial_diagnose.py segment-aware read

Sleeve repo, ~25 lines: filter the session metadata CSV to one segment's rows during the read (never accumulate all rows in memory), then fall back from a per-segment CSV name to the session CSV by stripping the -NNNN suffix.

Chunked reads in annotations.py / mvc.py

smart_sleeve_data_processing: a full 10-day session's metadata CSV is ~3.3 GB; a naive pd.read_csv will MemoryError. Needs chunksize= reads keeping only labeled rows per chunk.

embed_sync_anchor_marker.py session lock

Does a full read → backup → rewrite against the metadata CSV; must refuse to run while a session's CSV is still open, or it will corrupt a live file.

Full multi-day dry run

Everything validated so far ran for minutes. A complete dry run at real 15-minute segment length, ending in a clean stop and a full downstream ingestion, is the last step before the actual study.

05

Where this leaves things

Rotation itself is proven solid under real repetition (32 consecutive clean boundaries) and under a real fault (the gap landed exactly where the design intended, with the right markers in both the metadata and the manifest). The sync/ingestion data-loss bug found during this validation is real and still open, but it turned out to be scoped to the existing Box-based pipeline for non-patient data — the patient recording pipeline is separate and never touches it. On that basis video-segmentation has been merged to main. The other downstream readers (segment-aware reads, chunked metadata parsing) still need to catch up before a full 10-day recording's output moves cleanly through the rest of the study's pipeline, but none of that blocks recording the next patient.
