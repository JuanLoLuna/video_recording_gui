Video Recorder Phase 4

A second camera: a Firefly (720×540) beside the Blackfly S (1280×1024), both recording at 30 fps through one Thunderbolt dock, validated on the real rig with the video decoded and checked afterwards.

00

Summary

Phase 3 made the recorder reliable for one camera. This period added a second one without changing how a single camera records. The work ran in three passes: a feasibility probe on the rig, a rebuild of the camera layer around one controller per camera bound by serial number, and a series of headless recording runs on the real cameras that decode their own output.

Real hardware again found what review did not: a silent encoder fallback that wrote a segment of black frames with perfect timing, a worker thread that died on one filesystem error, and an SSD stall caused by plugging a device into the dock. Each is now detected or survived. Cross-camera synchronization was deliberately left out of scope, and the second camera's files are archive-only until the downstream pipeline learns the new file names.

What broke, and how it's handled

Eight findings. Hardware found the first three, the cable problem and the test-script problems; independent audits found the exposure lock and the stop-then-start bug.

01A fallback encoder wrote a segment of black frames and every live check passed
Symptom
Firefly segment 23 of run 140445 decoded to all-black frames. Its frame count, timestamps and metadata were perfect, so nothing in the app noticed.
Cause
→ OpenCV's FFMPEG writer could not create the file around a segment boundary and the constructor silently fell through to its built-in CV_MJPEG writer, which decodes grayscale as black on this rig. The same fallback recurred in runs 144535 and 150639; in 144535 the log also shows the mkdir error (WinError 183 while exists() was false) at the same moment.
Found by
A log line reading "opened on backend CV_MJPEG, not FFMPEG", then the operator decoding the whole folder: 1 bad segment of 61.
Result
Fixed in three layers: the writer is retried pinned to FFMPEG and the segment open fails rather than record with another backend; every finished segment's first frame is decoded and compared with the recorded frame (a "VIDEO PROBLEM" banner); the smoke script checks every segment. Runs 144535 and 150639 hit the event and recovered with no bad segment.
02One transient folder error killed the thread that finalizes segments
Symptom
In run 132903 the Blackfly stopped finalizing segments partway through: the manifest and events log were incomplete, 20 files stayed in .incomplete, and stopping waited 92.3 s before giving up.
Cause
→ A shared staging folder briefly misbehaved (WinError 183 creating it, WinError 3 listing it). Neither worker loop caught exceptions, so one error ended the only thread that closes segments.
Found by
The first MJPEG smoke run on the local drive; the Firefly in the same run passed.
Result
Fixed — folder operations retry, both worker loops log and continue, a failed segment still gets a manifest row, and the count shows in the banner. The cause of the folder glitch itself is unknown (open item).
03Plugging a device into the dock stalls the SSD for about five seconds
Symptom
When the Blackfly was plugged into the dock, the Firefly's longest write() took 5,032 ms and its queue reached 150 frames, then drained to 0. No frame was lost and capture never paused (longest gap 86 ms).
Cause
→ A USB event on the shared dock. The control run (laptop port to laptop port) showed none: longest write 16 ms, queue peak 1.
Found by
The smoke script's new per-camera diagnostics (longest write, longest capture gap), after a first run showed the queue spike without a cause.
Result
Handled, not fixed — the frames wait in memory. The writer-backlog and MJPEG warnings now require the backlog to hold for 10 s, so a stall that drains does not raise a false alarm.
04The exposure lock only reached the camera the controls pointed at
Symptom
With the first camera already on Off and the second on Continuous, starting preview at 30 fps left the second on auto exposure. Switching the "Adjust camera" selector also re-enabled the locked dropdown.
Cause
→ The lock only fired when the visible dropdown read something other than Off, and a replugged camera powers on in Continuous.
Found by
An independent audit and a probe that drove the real window against fake cameras.
Result
Fixed — the lock is applied to every camera every time, re-applied by the selector, and re-applied by the controller whenever it configures a camera (start and every reinit).
05Stop then Start could report success while recording nothing
Symptom
Pressing Start within seconds of Stop returned "already in progress" while the previous recording was still closing its last segment, so the window said it was recording and no video was written.
Cause
→ An existing bug on main: start_recording treated a recording that was being closed as one in progress.
Found by
Audit of the controller, not by hardware.
Result
Fixed — the start is refused with "previous recording is still closing", including the window where a start was accepted but not yet acted on.
06The MJPEG quality box never did anything
Symptom
The "%" box next to the MJPEG checkbox changed neither file size nor picture on any code path.
Cause
→ Quality cannot be set on the FFMPEG path (writer.set returns False, size unchanged); passing it as a constructor parameter made the FFMPEG writer refuse the call, so OpenCV fell back to its built-in writer, measured at about 800 ms per frame while writing over the slow cable of finding 07 (4–17 ms to local disk, so how much of that was the writer is only partly proven).
Found by
The MJPEG investigation, measured on frames from both cameras: about 42 dB PSNR, SSIM 0.965–0.976, 10× (Firefly) to 14× (Blackfly) smaller than raw.
Result
Fixed — the box is removed and MJPEG is documented as fixed quality. The study's existing video is already MJPEG at similar bitrates.
07Two cables silently ran at USB 2 speed
Symptom
The Firefly enumerated as HighSpeed, and the external SSD sustained about 48 MB/s (41 ms per 1.97 MB frame, against 7.9 ms after the swap).
Cause
→ A cable that negotiated down. Nothing in the app can tell a slow cable from a slow drive.
Found by
camera_inventory.py (link speed) and the writer latency probe.
Result
Fixed by swapping cables. Check the negotiated link speed first whenever something is unexpectedly slow.
08The test script's own checks were wrong four times
Symptom
Failures that were not recording problems: a fixed queue limit tripped at 60 fps (7 frames is 0.12 s), a run that stopped exactly on a segment boundary crashed the video check on an empty final segment, a 0.1% frame-rate tolerance failed 2–3 s test runs, and the final results sat unwritten in a buffer so a stuck run left a log that just stopped.
Cause
→ Thresholds copied from 30 fps, an untested edge case, and block-buffered output.
Found by
Rig runs and repeated local loops of the smoke tests.
Result
Fixed — limits scale with frame rate, empty segments are handled, the log is line-buffered, and a stuck stop now prints what each camera is waiting for.

The pattern: the worst problem (01) had a perfect frame count, perfect timing and perfect metadata. Only decoding the pixels found it. Checks that look at what was written, not at bookkeeping about writing, are what earned their place this period.

04

Open items

One-hour two-camera session in the application

The window ran for 13 minutes. A full-length session with 15-minute segments and a decoded-video check of the result is the remaining validation step.

Plain file names follow the lowest serial

The app uses whatever cameras are connected, so a different set of cameras can change which one has the plain names. The window shows which camera got them, and every events header records camera_serial and camera_model. SLEEVE_VIDEO_GUI_CAMERA_SERIALS is optional, for keeping one camera's names fixed.

Second-camera files and ingestion

Files with a _cam<serial> suffix do not match the naming rules in the downstream pipeline. They are archive-only until the first two-camera ingest, by decision; the proposed pattern is in the plan.

Why the staging folder flaps on C:

Unexplained. It appeared on the local drive only, around segment changes. Retries make it harmless; excluding the recording folder from real-time scanning is the test if it matters.

Uncompressed 60 fps final check

The capture was clean (queue peak 1) but the run printed nothing after its last progress line and the closing video check was never recorded. The script now reports where a slow stop is waiting.

MJPEG and the keypoint results

Quality is fixed at about 42 dB. The existing study video is already MJPEG, and a keypoint and joint-angle comparison is in progress on a separate branch.

05

Where this leaves things

Two cameras record together at 30 fps with MJPEG by default, hold 60 fps with room to spare, survive one camera being unplugged while the other keeps recording, and check their own video after writing it. A single camera behaves as before. What remains is operational: run one full hour through the application, and decide when to teach the downstream pipeline about the second camera's files.
