Summary

Phase 2 left six items open in the reliability backlog. With a real patient now scheduled for 9 days of continuous unattended recording, the top four were re-ranked and built this period: the power-safety modal that used to freeze the app and end the run, audio dropout handling, a native use-after-free risk in camera teardown, and the observability needed to tell a genuinely healthy multi-day run from a silently hung one. Two items (monotonic timestamps, sync pulse width) were folded in alongside since they touch the same session lifecycle and could be validated in the same hardware passes.

Every item was validated against real hardware, not emulated -- and real hardware testing found four genuine bugs beyond what a design review turned up, three of them fixed, one identified as a Windows/driver-level limitation outside this app's reach.

Three iterations against the same real failure, each one narrowing the diagnosis. Round 1 (name-only matching) reconnected to a different physical device within about one backoff attempt -- given away by audio_silence_frames_inserted=0, which should have been nonzero for a real gap. Round 2 added a host-API match, which turned out insufficient: this box reports 13 input devices, and at least two collide on both name and host API. Round 3 changed the matching philosophy entirely -- refuse to guess among ambiguous candidates rather than silently pick one -- and the final retest showed audio_reconnects staying at exactly 0 for the whole session despite a live mic swap being visibly observed. That is the clinching data point: nothing failed at the PortAudio level at all, so the swap is happening one layer below anything this app (or any PortAudio-based app) can detect -- most likely Windows or a driver auto-substituting a fallback device before the disconnection is ever reported. See finding 04.

What broke, and how it's handled

Four findings this period, all surfaced only by real hardware testing -- none were visible from code review alone.

01Stop Preview stayed clickable during a power pause, with no way back
Symptom
While paused for power safety, the Stop Preview button was still enabled. Clicking it dropped state to CAMERA_DETECTED, and auto-resume only fires from PREVIEWING -- an accidental click would silently strand the run for the rest of the session with no way to resume.
Cause
→ _apply_state()'s PREVIEWING branch didn't account for the new paused sub-state when it was introduced -- it only ever disabled the record button.
Found by
The user clicking around during the power-pause hardware test, not anticipated in the design.
Result
Fixed — the preview button is now disabled for the same reason and duration as the record button while paused.
02Silent stream drop: the common Windows unplug path had zero console feedback
Symptom
The user reported "no feedback when I unplugged the mic -- nothing" during the first mic test.
Cause
→ The drop-detection print only fired inside an except Exception block, but Windows/WASAPI commonly ends a stream gracefully on unplug (stream.active just goes False, nothing raises) -- that far more common path logged nothing at all.
Found by
Direct user observation during hardware testing, cross-checked against the fact the diagnostics CSV showed no reconnect activity either.
Result
Fixed — both the graceful-end path and a periodic "still trying to reconnect" line during a long outage now print unconditionally.
03Mic reconnect silently locked onto the wrong physical device
Symptom
A few seconds after unplugging the USB mic, the level meter went dead and stayed dead -- including after replugging the real mic.
Cause
→ resolve_device_index_by_name() matched on device name alone. This test box has 13 input devices, and at least two report the identical name (a generic driver-supplied string), so the reconnect grabbed whichever matched first -- confirmed by audio_silence_frames_inserted=0, meaning it matched almost instantly rather than after a real gap. A host-API match (round 2) narrowed but didn't eliminate the collision.
Found by
Reading _diagnostics.csv's audio columns against the user's live description of the symptom, across three iterations.
Result
Fixed — the matcher now refuses to pick among multiple candidates at all, rather than guessing. Recording silence from a wrong device with no indication is worse than staying visibly disconnected; this trades into the honest failure mode even though a genuine collision may never auto-resolve.
04This box's mic fallback happens below where any PortAudio app can see it
Symptom
Even after finding’s 02 and 03 were fixed, the same wrong-device swap still happened -- but the retest's diagnostics showed audio_reconnects=0 for the entire session.
Cause
→ Zero reconnect activity despite an observed live swap means the app's stream never actually failed. Windows or a driver is auto-substituting a fallback device at a layer below PortAudio, so there is nothing for this app's reconnect logic to react to -- the disconnection is never reported at all.
Found by
Cross-referencing the confirmed-clean matching logic (findings 02, 03) against a diagnostics file showing zero reconnect events during an observed swap.
Result
Handled, not fixed — there is no code fix available at this layer. Documented as a known OS/driver-level limitation specific to this box; not chased further since the upcoming patient recording doesn't use a microphone.

The pattern across all four: real hardware testing, not design review, found every one of them -- consistent with every prior phase of this project. Finding 04 is also a reminder that "the reconnect logic never engaged" and "the reconnect logic worked perfectly" look identical from inside the app when the failure is masked one layer down; the diagnostics CSV's zero counters were what made the distinction legible.

Open items

Overnight soak test

Phase 1's leftover validation item -- everything tested so far, across all three phases, has run for minutes, not hours or days. The user is running this next.

Unexplained 4.4s session stop

recording_20260828_131603 stopped after 129 frames via an ordinary session_stop, too fast for the power-pause debounce (which needs 10s) to have caused it, and disk guard doesn't monitor mid-session. Most likely a manual stop; not reproducible, not chased further.

Mic OS-level fallback (this box only)

Finding 04 above. Fixable only via Windows/driver audio settings on that specific machine, not in this app's code. Not relevant to the upcoming patient recording, which uses no microphone.

Full multi-day dry run

Everything validated across all three phases so far ran for minutes to a couple hours. A complete dry run at real segment length, ending in a clean stop and full downstream ingestion, remains the last step before the actual study -- per the original plan.

05

Where this leaves things

All four originally-ranked Phase 3 items, plus the two folded in alongside them, are now shipped and hardware-validated: power pause/resume no longer freezes the app or ends a run, camera-fault recovery and rotation both hold up under two real faults in one session with the new timeline columns intact, teardown no longer risks a use-after-free on a stuck thread, and a returning operator has an actual "healthy for" readout instead of a permanent-latch warning. Audio dropout handling is real and correct code, verified as far as this specific test box's Windows configuration allows it to be verified -- the remaining gap there is a driver-level limitation, not an open bug, and doesn't affect the patient recording. What's left before the study itself is operational, not code: the overnight soak test and the full multi-day dry run.
